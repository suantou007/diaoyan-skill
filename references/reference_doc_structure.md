# 参考：产品调研报告模板

只要本 skill 产出 **飞书文档或 `notes.html`**，就必须使用这份结构作为信息收集与组织的主框架；前提是本地 evidence package 已经完成。

如果用户明确只要快速草稿，可以降级，但必须在最终回复里说明“未按正式报告结构完整展开”。除此之外，不允许把本文件当可选参考。

来源：Lark Wiki `CodewL09NilctEkYl65cB2dVndc` —— “产品调研文档模板”。这是当前默认的目标报告模板。

## 文档结构

### 1. 一句话总结

文档顶部放一个 callout，格式固定为：

```text
{一句话定位} · {一句话亮点} · {一句话现状描述（发展方向、投资、变动）}
```

关键原则：

- 不是中性百科介绍，而是让读者 10 秒内理解产品是什么、最值得注意的点是什么、当前处在什么状态。
- 一句话定位要能和“基本信息 > 产品定位”保持一致。
- 一句话亮点必须能在“核心功能体验”或“亮点与不足”里找到证据支撑。

### 2. 基本信息

用表格呈现：

| 项目 | 内容 |
|-|-|
| 产品名 |  |
| 所属公司 / 团队 | （来源：xxx） |
| 上线时间 | YYYY.MM（来源：xxx） |
| 平台 | iOS / Android / Web / 小程序 |
| 产品定位 | 一句话定位 |
| 目标用户 | 一句话用户画像 |
| 关键数据 | DAU / MAU / 下载量 / 融资（来源：xxx） |
| 官网 / 下载 | 链接 |

规则：

- 视频中未覆盖的字段由 AI 检索补全，并在该字段后用“（来源：xxx）”标注。
- 查不到则写“未公开”，不要删除字段。
- “产品定位”是后文结论的锚点，不能和最后的“核心判断”互相打架。

### 3. 产品简介

用 150–250 字自然段说明：

- 这是什么产品
- 解决什么需求
- 主体验是什么
- 当前所处阶段

这里不展开功能细节，只建立读者理解产品所需的背景。

### 4. 核心功能体验

这是文档主体，按视频中出现顺序写。每个功能模块固定写法：

```text
小标题 → 简述 → 体验截图 → 截图描述 → 一句点评
```

每个模块至少包含：

- **简述**：2–4 句话讲清楚功能干什么、怎么用、关键交互。
- **体验截图**：放对应截图，并标注来源视频时间戳（如 `mm:ss`）。
- **截图描述**：说明读者应该看见什么，而不是堆“用于证明”。
- **一句点评**：明确亮点或问题在哪里。

选择规则：

- 优先选“与竞品差异最大”和“用户感知最强”的功能。
- 不要流水账式全覆盖；通常 3–6 个功能模块足够。
- 标题可以按视频顺序，但要尽量写成用户能理解的能力模块，而不是“点击按钮 / 打开菜单”。
- 亮点与不足里的每条判断，原则上都要能回指到这里的某个功能模块或截图。

### 5. 亮点与不足

聚焦“本产品自身”的体验感知，不默认展开竞品对比。

#### 亮点

- 每条 1 句话
- 总数控制在 6 条以内
- 每条都应能在“核心功能体验”里找到对应支撑

#### 不足

- 每条 1 句话
- 总数控制在 6 条以内
- 每条都应能在“核心功能体验”或“未展示 / 未核验”记录里找到依据

### 6. 竞品对比

用表格呈现：

| 产品 | 定位 | 目标用户 | AI 能力 | 与本产品的差异点 |
|-|-|-|-|-|
| {本产品} | — | — | — | — |
| {竞品 1} | （来源：xxx） |  |  |  |
| {竞品 2} | （来源：xxx） |  |  |  |

规则：

- 竞品由 AI 检索同赛道头部 2–3 个产品填入。
- 无法判断赛道时写“待补充”。
- 竞品对比只做关键差异，不要变成参数抄表。
- 如果用户指定“我方产品”或重点竞品，优先使用用户指定对象。

### 7. 结论与跟踪建议

固定包含：

```text
核心判断：一句话。

值得持续跟踪的变量：
1. ……
2. ……
```

规则：

- “核心判断”必须和“基本信息 > 产品定位”一致，不能前面说是工具、结论却当平台判断。
- 跟踪变量优先围绕产品能力、增长信号、商业化、竞品压力、关键未核验信息。

### 8. 一致性检查

报告尾部必须增加“一致性检查”，至少回答：

1. **产品定位 vs 核心判断**：基本信息里的“产品定位”和结论里的“核心判断”是否一致？如果不一致，说明以哪个为准并修正文档。
2. **亮点 / 不足 vs 核心功能体验**：亮点和不足是否能在核心功能体验里找到对应支撑？如果找不到，要么补充截图/描述，要么删除该判断。

建议格式：

| 检查项 | 结论 | 处理 |
|-|-|-|
| 产品定位与核心判断一致性 | 一致 / 不一致 | 如不一致，说明已修正到哪里 |
| 亮点是否有功能体验支撑 | 全部有 / 部分缺失 | 列出缺失项和处理 |
| 不足是否有功能体验支撑 | 全部有 / 部分缺失 | 列出缺失项和处理 |

### 9. 附录：信息来源

至少包含：

- 体验视频：`{视频名称 / 时长}`
- 外部检索：`{检索工具}`（`{关键词 1}`、`{关键词 2}`……）
- 其他参考：官方页面、文档、定价页、评论来源等

## 缺失信息处理

每个模块都要尝试收集。没有查到时，写明：

- `未公开`：公开信息中没有可靠来源
- `未找到`：搜索过但没有可靠来源
- `未核验`：有线索但没有一手来源确认
- `视频未展示`：视频没有直接证据
- `不适用`：该维度确实不适合该产品

不要因为信息缺失就删除整个字段或模块。

## 关键格式模式

- **Callout**：用于“一句话总结”和必要提醒。
- **表格**：用于“基本信息”“竞品对比”“一致性检查”。
- **图片 / grid**：用于“核心功能体验”，多步骤流程可用 2–4 张图并排。
- **引用**：用于外部评价或用户原话，但不是必填模块。

## 结构经验

- 先规划全结构，再发布，不要一边插图一边修文档结构。
- “核心功能体验”是证据主干；亮点、不足、核心判断都要能回指到它。
- HTML 与飞书默认共用这套章节结构，不要让 HTML 退化成审计页、飞书才像正式报告。
- 图和截图必须贴近对应功能模块，不要集中堆到文档末尾。
