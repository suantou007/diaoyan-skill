# 参考：产品调研报告模板

只要本 skill 产出 **飞书文档或 `notes.html`**，就必须使用这份结构作为信息收集与组织的主框架；前提是本地 evidence package 已经完成。

如果用户明确只要快速草稿，可以降级，但必须在最终回复里说明“未按正式报告结构完整展开”。除此之外，不允许把本文件当可选参考。

来源：Lark Wiki “产品调研文档模板”

- 模板链接：https://my.feishu.cn/wiki/CodewL09NilctEkYl65cB2dVndc
- CLI 解析后的 Docx 链接：https://bytedance.larkoffice.com/docx/WvkSdNbOIoWMQWxz4qKczdH0nge

这是当前默认的目标报告模板；如果飞书模板继续调整，本文件也要同步更新。

## 文档结构

### 1. 一句话总结

文档顶部放一个 callout，格式固定为：

```text
{一句话定位} · {一句话亮点} · {一句话现状描述（发展方向、投资、变动）}
```

关键原则：

- 不是中性百科介绍，而是让读者 10 秒内理解产品是什么、最值得注意的点是什么、当前处在什么状态。
- 一句话定位要能和“基本信息 > 产品定位”保持一致。
- 一句话亮点必须能在“核心功能体验”或“亮点与不足”里找到证据支撑。
- callout 里只写结论，不写 `【注意】`、执行说明、检索说明或 agent 过程。

### 2. 基本信息

用表格呈现：

| 项目 | 内容 |
|-|-|
| 产品名 |  |
| 所属公司 / 团队 | （来源：具体可访问链接或页面名） |
| 上线时间 | YYYY.MM（来源：具体可访问链接或页面名） |
| 平台 | iOS / Android / Web / 小程序 |
| 产品定位 | 一句话定位 |
| 目标用户 | 一句话用户画像 |
| 融资 / 投资 | 金额、轮次、时间、投资方；没有可靠来源时写“未公开 / 未找到” |
| 用户规模 | DAU / MAU / 下载量 / 注册用户 / 客户数量，优先给具体数字和时间口径 |
| 定价计划 | 至少列出 3 个公开档位的价格、计费周期、额度 / 限制；不足 3 档时说明官网只公开了哪些 |
| 官网 / 下载 | 链接 |

规则：

- 视频中未覆盖的字段由检索补全，并在该字段后用“（来源：具体可访问链接或页面名）”标注。
- 查不到则写“未公开”，不要删除字段。
- “产品定位”是后文结论的锚点，不能和最后的“核心判断”互相打架。
- “关键数据”不能只写泛泛表述；优先追具体金额、具体人数 / 用户量、具体价格。
- 融资、用户规模、定价计划必须尽量引用可访问来源。Tavily 没抓到时必须继续 WebSearch；仍找不到才写“未公开 / 未找到”。

### 3. 产品简介

用 150–250 字说明，保留自然可读性，但必须用加粗锚点组织：

- **产品定位**：这是什么产品
- **核心需求**：解决什么需求
- **主体验**：用户主要如何使用
- **当前阶段**：发展、融资、商业化或市场状态

这里不展开功能细节，只建立读者理解产品所需的背景。

### 4. 核心功能体验

这是文档主体，按视频中出现顺序写。每个功能模块固定写法：

```text
小标题 → 简述 → 体验截图 → 截图描述 → 一句点评
```

每个模块至少包含：

- **简述**：2–4 句话讲清楚功能干什么、怎么用、关键交互。
- **体验截图**：放对应截图，每张图必须有短图注；必要时在图注末尾标注视频时间戳（如 `mm:ss`）。
- **截图描述**：说明读者应该看见什么，而不是堆“用于证明”。
- **一句点评**：明确亮点或问题在哪里。

选择规则：

- 优先选“与竞品差异最大”和“用户感知最强”的功能。
- 不要流水账式全覆盖；通常 3–6 个功能模块足够。
- 标题可以按视频顺序，但要尽量写成用户能理解的能力模块，而不是“点击按钮 / 打开菜单”。
- 亮点与不足里的每条判断，原则上都要能回指到这里的某个功能模块或截图。
- 正式报告默认先保留 **至少 16 张候选截图**，再从中筛出 **8–10 张** 放进飞书正文。
- 每个核心功能模块默认使用 **1–2 张图**；如果一个模块只有 1 张图，通常需要确认是不是遗漏了过程态或结果态证据。
- 入口 / 结果、前 / 后、多个候选方案、多个竞品界面等并列关系图片，必须用 grid / 分栏放在同一行。

### 5. 亮点与不足

聚焦“本产品自身”的体验感知，不默认展开竞品对比。

#### 亮点

- 每条 1 句话
- 总数控制在 6 条以内
- 每条都应能在“核心功能体验”里找到对应支撑

#### 不足

- 每条 1 句话
- 总数控制在 6 条以内
- 每条都应能在“核心功能体验”或“未展示 / 未核验”记录里找到依据

### 6. 竞品对比

用表格呈现：

| 产品 | 定位 | 目标用户 | AI 能力 | 与本产品的差异点 |
|-|-|-|-|-|
| {本产品} | — | — | — | — |
| {竞品 1} | （来源：具体可访问链接或页面名） |  |  |  |
| {竞品 2} | （来源：具体可访问链接或页面名） |  |  |  |

规则：

- 竞品从同赛道头部 2–3 个产品中选择填入。
- 无法判断赛道时写“待补充”。
- 竞品对比只做关键差异，不要变成参数抄表。
- 如果用户指定“我方产品”或重点竞品，优先使用用户指定对象。

### 7. 结论与跟踪建议

固定包含：

```text
核心判断：一句话。

值得持续跟踪的变量：
1. ……
2. ……
```

规则：

- “核心判断”必须和“基本信息 > 产品定位”一致，不能前面说是工具、结论却当平台判断。
- 跟踪变量优先围绕产品能力、增长信号、商业化、竞品压力、关键未核验信息。

## 不进公开正文的内容

以下内容必须做，但默认不发布到飞书正文或 `notes.html`：

- 一致性检查：产品定位 vs 核心判断；亮点 / 不足 vs 核心功能体验。
- 执行过程：使用了哪些工具、重试了几次、Tavily / WebSearch 的分工。
- 检索失败明细：只在对应字段写“未公开 / 未找到 / 未核验”，完整过程放 `analysis_manifest.json`。
- 附录信息来源：默认不设；如果用户明确要求，或关键数据需要透明来源，只列 WebSearch / Tavily 返回的可访问网页链接或具体 URL。

## 缺失信息处理

每个模块都要尝试收集。没有查到时，写明：

- `未公开`：公开信息中没有可靠来源
- `未找到`：搜索过但没有可靠来源
- `未核验`：有线索但没有一手来源确认
- `视频未展示`：视频没有直接证据
- `不适用`：该维度确实不适合该产品

不要因为信息缺失就删除整个字段或模块。

## 关键格式模式

- **Callout**：只用于“一句话总结”或极少数核心结论，不用于 `【注意】` 或过程提醒。
- **表格**：用于“基本信息”“竞品对比”。
- **图片 / grid**：用于“核心功能体验”，多步骤流程和并列关系图片必须 2–4 张并排。
- **引用**：用于外部评价或用户原话，但不是必填模块。

## 结构经验

- 先规划全结构，再发布，不要一边插图一边修文档结构。
- “核心功能体验”是证据主干；亮点、不足、核心判断都要能回指到它。
- HTML 与飞书默认共用这套章节结构，不要让 HTML 退化成审计页、飞书才像正式报告。
- 图和截图必须贴近对应功能模块，不要集中堆到文档末尾。
