# 参考：对外展示版竞品报告结构

只要本 skill 产出 **飞书文档或 `notes.html`**，就必须使用这份结构作为信息收集与组织的主框架；前提是本地 evidence package 已经完成。

如果用户明确只要快速草稿，可以降级，但必须在最终回复里说明“未按正式报告结构完整展开”。除此之外，不允许把本文件当可选参考。

来源：Lark 文档 `CjfpdyinQo1df5xrQlvl7iTBgnb` — “Topview AI【敏捷研究】”

这份结构展示了一份成熟竞品报告通常该怎么排版与组织内容。

## 文档结构

### 1. 执行摘要 Callout（light-orange）

文档顶部放一个 callout，把产品定位和竞品判断放在一起，不再单独做“优势与不足总结”章节。

推荐结构：

- **一句话介绍**：它是谁做的、服务谁、主打什么
- **核心亮点**：1–3 条最值得关注的竞争优势
- **对比[我方产品]或主要竞品的差异和不足**：1–2 条关键短板，重要问题用 `<text color="red">` 标出来；如果用户没有给“我方产品”，就与主要竞品/替代方案比较

关键原则：这里要有观点、有比较，不要写成中性百科介绍。读者应该在 10 秒内看懂这个产品值不值得重视。

Callout 之后，默认再补 **2–4 段总括**，回答：

- 为什么这个产品值得关注
- 当前最强的产品信号是什么
- 最大风险或最不确定的地方在哪里

也就是说，执行摘要不要只是一块 callout 就结束。

### 2. 公司与团队

#### 基本信息

- 成立时间、总部地点
- 是否有母公司
- 融资轮次、金额、领投方、用途

#### 创始人与核心成员

- CEO、CTO 或核心团队成员背景
- 过往公司与角色
- 与当前产品最相关的领域经验

#### 用户与客户

- SimilarWeb 等来源的流量信号
- 对用户量的谨慎估计
- 与其他竞品的流量对比
- 典型客户类型、已知品牌客户

### 3. 产品介绍

#### 核心功能

- 推荐先用 **lark-table** 做一个简洁总表，列为：功能 | 视频证据 / 结论 | 竞争意义
- 每一行对应一个核心功能
- 关键功能再往下展开成小节：小标题 + 图片 + 简洁图注 + 判断
- 图片应直接放在对应功能行 / 对应功能小节内部，不要把图片都堆到后面的单独“证据拆解”章节
- 图注要简洁，像“径向菜单：把专业工具栏游戏化”，不要写成“用于证明：……”
- 最突出的功能可以用 `<text bgcolor="light-yellow">` 高亮
- 有亲自试用结论时可以补进去，但要标清来源
- 功能描述要具体，不要只写大词
- 如果要补“核心工作流 / 用户路径”，默认把它作为本章最后一个小节放入，而不是再单独抬一个并列大章
- 默认按 **能力主题** 合并标题，不要把“打开菜单 / 选择 variant / 点击 capture”这类细动作都拆成独立小节
- 每个功能小节默认至少写到 **2–4 段分析**，而不是只放图后接一句判断

更推荐的标题方式：

- `世界优先的创作入口`
- `多模态输入与快速试错`
- `场景上下文驱动的迭代闭环`

不推荐：

- `打开右键菜单`
- `选择候选结果`
- `框选场景区域`

#### 产品定位和优势

- 2–3 段说明它在市场中的定位
- 总结 2–3 条关键竞争优势

#### 售卖方式和定价

- 用 **lark-table** 整理 Free / Starter / Business / Enterprise 等套餐
- 至少写价格、额度、关键限制、是否带水印、其他差异
- 如果同时有 API 定价，也要单独说明

#### 产品评价

- 评价来源可以来自 **G2**、**ProductHunt** 等
- 同时保留正面和负面反馈
- 评论引用用 `<quote-container>`
- 能配截图时更好
- 最后总结整体口碑与常见抱怨

### 4. 横纵分析

正式研究里，纵向与横向默认收束成一个完整章节，而不是互相割裂的两块。

推荐拆法：

- **4.1 纵向演进**：诞生背景、关键里程碑、阶段变化
- **4.2 横向竞品对比**：与主要竞品 / 替代方案对比
- **4.3 交汇洞察**：为什么它今天会处在这个位置、优势和短板分别来自哪段历史

关键原则：

- 不要把纵向演进写成编年史
- 不要把横向对比写成参数抄表
- 交汇洞察必须把时间线和竞争格局真正连起来
- 本章结尾要有一个更完整的总结段，回答“所以我们最终怎么看它”

### 5. Demo 视频

- 原始录屏尽量用可播放的 `<file>` + `<view type="2">` 嵌进去
- 如果有“输入 vs 输出”对比，适合用 `<grid cols="2">`
- 读者通常更愿意自己看几段原视频，而不只是看静态截图

### 6. 相关链接

- 可用 `<mention-doc>` 链接到相关分析文档

**不要再单独做“优势与不足总结”章节。** 竞品判断已经放在顶部 callout 里。

## 关键格式模式

- **Callout**：`<callout emoji="..." background-color="light-orange">`
- **表格**：`<lark-table>`
- **图片网格**：`<grid cols="2">` + `<column>`
- **引用**：`<quote-container>`
- **高亮**：`<text bgcolor="light-yellow">`、`<text color="red">`
- **视频嵌入**：`<view type="2"><file token="..." name="..."/></view>`

## 缺失信息处理

每个模块都要尝试收集。没有查到时，写明：

- `未找到`：搜索过但没有可靠来源
- `未核验`：有线索但没有一手来源确认
- `视频未展示`：视频没有直接证据
- `不适用`：该维度确实不适合该产品

不要因为信息缺失就删除整个模块。

## 结构经验

- **主功能章节控制在 3–6 个能力主题**，不要拆得太碎
- **标题写洞察，不只写名词**，例如“生成时自动弹出项目选择器”优于“视频生成与积分消耗”
- **多步骤流程使用 2–4 张图的 grid**，不要硬塞成单图
- **不要默认重复写“时间戳 / 来源”这种低价值字段**；只在真正帮助判断时出现
- **不要单独做“证据拆解”大章**；截图应跟着对应功能走
- **HTML 与飞书默认共用这套章节结构**；不要让 HTML 退化成审计页、飞书才像正式报告
- **每节都要有收束判断**；不要标题很细、内容却很薄
- **先规划全结构，再发布**，不要一边插图一边修文档结构
